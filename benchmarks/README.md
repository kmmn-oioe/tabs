# 実曲のTAB比較テスト

このテストは、添付された原曲とTAB動画から作成した短い手動注釈と、現在のアプリの出力を比較します。学習や曲専用の判定条件の追加は行いません。

## 最初のケース

`cases/unmei_intro.json` は「運命に賭けたい論理」のTAB動画の第2〜6小節を転記したものです。リード40音、リズム45音、計85音。原曲約1.68〜9.84秒の発音に加え、その直前の両パートの休符区間を評価します。全曲・全楽器の正解データではありません。動画の演奏が実録音と完全に一致する保証もありません。

- 上段Lead・下段Rhythmを別々のパートとして記録。
- TABに表示される147 BPMの8分音符グリッドを使用。
- 原曲時間 = TAB動画時間 + 約1.087347秒。複数の10秒窓の波形相互相関で同じずれを確認しました。相関値・確認箇所はJSON内に記録しています。
- 第2小節の頭は原曲1.680秒。カーソル・発音からの読み取り誤差は約40 msを見込みます。結果を見て正解時刻を最適化することはしていません。
- 動画のカポ1・実音表記を五線譜と照合し、表示フレットをナット基準として読み取りました。JSONのフレットはカポからの相対位置へ変換済みです。`pitch = tuning[string] + capo + fret`、弦番号は0=1弦です。
- 音の終了は譜面上の音価です。実録音の減衰・残響は注釈していません。

音源・動画そのものはリポジトリへ含めません。ファイル名・元URL・SHA-256のみ記録しています。実曲テストの再実行には、ユーザーが添付した同じMP3が必要です。

## 再実行（Windows）

プロジェクトのフォルダーで実行します。`--audio`には添付MP3の実際のパスを指定してください。ファイルが違う場合は、時刻の対応が崩れるのを防ぐためSHA-256照合で停止します。

```bat
.venv\Scripts\python.exe -m tabgen.evaluate run --reference benchmarks\cases\unmei_intro.json --audio "C:\音源\Official Music Videoトゲナシトゲアリ運命に賭けたい論理 - アニメガールズバンドクライ.mp3" --output benchmark-output\auto
```

原曲の先頭0〜10.3秒を解析する条件を固定しています。前後に文脈を含む全曲解析とはBPM推定や声部追跡の結果が異なる可能性があります。既定は分離なしです。`--separation`を付けるとアプリと同じDemucs分離を要求し、実際に適用されたかも記録します。分離の有無が違う結果を同じ条件として比較しないでください。

`--full-context`を付けると全曲を解析し、採点は同じ85音だけに限定します。
短いテスト区間だけで改善して全曲入力では消えてしまうことを検出するための条件です。
解析範囲と採点範囲、選別方法はレポートに別々に保存します。

`--rhythm-mode notes`で検出した発音を残す新モードを採点できます。
省略時の`chords`は従来のコード保持モードです。BPM・分離の有無・解析範囲をそろえて比較してください。

BPMの影響を切り分ける診断も用意しています。

```bat
.venv\Scripts\python.exe -m tabgen.evaluate run --reference benchmarks\cases\unmei_intro.json --audio "C:\音源\Official Music Videoトゲナシトゲアリ運命に賭けたい論理 - アニメガールズバンドクライ.mp3" --output benchmark-output\reference-tempo --tempo-mode reference
```

`reference`は正解の147 BPM・グリッド原点をアプリへ与えます。自動採譜の性能としては扱わず、`auto`とは別の条件で比較してください。正解のノートやパートをアプリに与えることはありません。

出力:

- `report.md`: 各段階・パートの一覧表。
- `report.json`: 一致数、適合率・再現率・F1、追加・欠落した各音、パートの取り違え、発音ずれ、譜面上の終了位置との差、運指一致率、許容差の感度。
- `diagnostics.json`: 音程候補、選別後・量子化前のリード、最終リード／リズムと設定。これを残せばモデル推論を繰り返さず再採点できます。
- 自動BPMでは、検討した複数のBPM候補とスコア、選択したBPM・原点、情報不足時の仮設定も記録します。
- 音声判定を使う場合は、その直後の候補・各音の証拠スコア・使用した判定方法も記録します。音声判定で落ちた音と旋律追跡で落ちた音を区別できます。
- `tab.txt`: その試行の画面用TAB。

```bat
.venv\Scripts\python.exe -m tabgen.evaluate compare --reference benchmarks\cases\unmei_intro.json --diagnostics benchmark-output\auto\diagnostics.json --output benchmark-output\auto\rescored.json --tolerance-ms 100
```

## 採点方法

MIDI音高が一致し、開始時刻の差が±80 ms以内の音を対応づけます。最終出力はパートも一致が必要です。同じ検出音を複数の正解へ重複計上しないよう、最大一致数を求めてから発音誤差を小さくする一対一対応を使います。対応しない出力音が「余計な音」、対応しない正解音が「抜けた音」です。

F1は適合率と再現率の調和平均です。正解・出力とも0音なら満点にはせず未定義とします。パート不問の対応とパート一致の対応を分け、声部の誤りを確認できます。同じ時刻・音高が両パートにある場合は正解2音として扱います。

- 生の音程候補には歌・ベース等も含まれます。候補段階の適合率を、ギター単体の誤検出率と解釈しないでください。正解のギター音が候補に残っていたかを見る再現率が主な手掛かりです。
- リズムの`chords`モードはコード保持の伴奏への編曲です。原譜のアルペジオを再現しないことも「抜けた音」に含みます。`notes`モードは残りの検出音を使い、誤検出や声部の取り違えも出力へ残ります。
- 違う運指でも同じ音は出せるため、運指一致率は別の参考値です。
- 短い区間の手動注釈なので、曲全体の精度へ一般化しません。50/80/100 msの許容差による変化も出力します。

[初回比較結果](results/unmei_intro_baseline.md)と[機械可読の要約](results/unmei_intro_baseline.json)を保存しています。改善後は同じ音源・範囲・設定で再実行して比較します。詳細な音ごとの結果は実行時に生成し、公開リポジトリには要約を保存します。

リード選別を変更した結果は[改善前後の比較](results/unmei_intro_lead_improvement.md)に保存しています。
短区間と全曲入力を別条件で比較し、以前の「羽が生えた理由」の冒頭にリードを追加しないことも確認しています。

続く[テンポ推定の改善結果](results/unmei_tempo_improvement.md)では、同じリード判定を使ったまま、
BPM・グリッド原点の修正による最終TABの違いを比較しています。

[リズム発音を残すモードの比較](results/unmei_rhythm_notes.md)では、同じテンポ・同じリード判定で
`chords`と`notes`を比べ、一致する発音の増加と余計な音の増加を両方記録しています。

[Demucs分離あり／なしの比較](results/unmei_demucs_comparison.md)では、BPMと拍の原点を共通指定し、
ギター専用の`htdemucs_6s/guitar`で効果を測定しました。分離の未実行や`other`への代替を
ギター専用分離の成功として扱わず、実際のモデル・出力の長さ・ハッシュも記録しています。

1. 検出候補に残っている旋律音をリード選別で落とす問題を調べる。
2. 原譜のアルペジオを維持する出力と、コード伴奏への編曲を区別する。
3. この短区間で起きたBPMの取り違えを調べる。テンポを正解に固定するだけでは今回のリード欠落は解決しません。

通常のテストでは採点器の一対一対応、誤パート、休符、重複、運指・カポ、注釈の自己整合性、診断取得による出力不変を検証します。実曲モデルの推論はMP3が必要なため、通常の単体テストには含めません。
